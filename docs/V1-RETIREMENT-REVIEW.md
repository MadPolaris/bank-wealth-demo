# `v1/` 目录退役评估

日期：2026-11-06。状态：**已完成退役评估，后续精简任务已明确；本次提交前尚未实施迁移或删除。** 最初用户问“除了tree退役了，是不是v1也该退役了”时只做评估。随后用户要求“先提交，给我一个压缩上下文的窗口，后面继续推进进展，并且精简 bank-wealth-demo 的内容”，据此登记下一批现役/历史内容精简；不把概括性精简要求扩大为盲删旧数据、改金融政策或协议版本。

## 结论

应该让 `v1/` 退出当前开发入口，但不能整目录删除，也不应把所有路径简单改成 `v2/`。

`tree/` 是已被唯一新作者树替代的输入；`v1/` 现在却混放仍在执行的手写代码、仍用于验收的独立测试、旧编译输入、发行证据与第三方许可。混合目录让新人误以为“v1全是旧的”或“新开发必须继续编辑历史快照”。应按职责拆开，而不是继续把版本号当目录架构。

## 为什么现在不能直接删除

- `truthsrc.project.json:295–296` 明确挂载 `./v1/handwritten/scala`。
- `tools/verify-truthsrc-build.mjs:29` 定义实际手写根；生成的build及实际staging也核对它。
- `tools/truthsrc-actor-tests.mjs:35`、`tools/truthsrc-readside-tests.mjs:64`、`tools/truthsrc-runtime-tests.mjs:27` 仍从 `v1/test/scala`读取固定业务预期。
- 新工作坊的来源捕获、启动、回执和运行准入均依赖这些真实文件；仅改README不会解除依赖。
- 历史发行/旧工具仍有明确的 `--historical` 分支和固定请求读取。新入口没有使用它们，不等于历史消费者可以无条件删掉。

## 推荐的迁移合同

1. 先固定当前作者/产品/生成结果、35份手写和31份测试的独立路径及SHA清单。
2. 将现役代码/测试按职责迁出，内容逐字节保留。只改路径接线、显式manifest和文档；不改金融政策或测试期望。
3. 迁移当前架构合同、手写来源映射和必须携带的许可证；旧发行/阶段回执继续以原版本/原地址解释，不改写原证据。
4. 更新根项目、构建准入、运行准入、沙箱路径、供给/打包和测试入口，不用symlink伪装旧目录仍现役。
5. 历史输入只在明确历史入口读取；仍需随新clone运行的测试fixture不能只留维护者机器。纯研究/旧发行资料可通过固定Git对象和原归档定位，不能编造下载渠道。
6. 在新候选执行严格编译、图/精确回锚、代码与固定银行业务测试。路径影响生成build、输入摘要和回锚，必须产生新回执；目录改名不是旧验收自动有效的证明。
7. 核当前默认命令无 `v1/handwritten`/`v1/test` 等路径依赖后，才移除混合目录。固定历史URL/版本字样保留明确说明，不机械全局替换。

## 这些“v1”不随目录退役

- `/api/v1` 和 `/bank/v1` 是公开HTTP/API版本。
- `canonicalId: bank-v1` 是输入身份；改它会影响知识来源键。
- `bank-v1-1`、codec IDs、Saga/pipeline定义版本、protobuf/PID及冻结runtime版本属于协议/业务合同。
- 1134发行及其历史签出继续有效于原范围。

**退役的是混合文件容器，不是取消银行V1业务，不是发布V2，也不是重写已有持久化数据。** 此迁移建议独立成一个有起止门的收口批次，不能夹带进当前新手图/验收包装或以删除冻结测试缩短交付。
